## 2. 踩坑清单

### P1 `nvv4l2h264enc` 拒绝系统内存帧 → 必须先 `nvvidconv`

- **现象**：`gst_parse_error: could not link videoconvert0 to nvv4l2h264enc0, nvv4l2h264enc0 can't handle caps video/x-raw, format=(string)I420`
- **根因**：Jetson 的 `nvv4l2h264enc` sink 只接受 `video/x-raw(memory:NVMM)`，CPU 侧的 I420 帧必须搬进 NVMM 显存。
- **排查**：`gst-inspect-1.0 nvv4l2h264enc` 看 pad template 的 caps。
- **解法**：在编码前插 `! nvvidconv ! video/x-raw(memory:NVMM),format=NV12`。
- **最终 pipeline**（见 `src/RtmpPublisher/RtmpPublisher.py`）：
  ```
  appsrc name=src is-live=true do-timestamp=false format=time
    caps=video/x-raw,format=BGR,width=640,height=360,framerate=30/1
  ! videoconvert ! video/x-raw,format=I420
  ! nvvidconv ! video/x-raw(memory:NVMM),format=NV12
  ! nvv4l2h264enc bitrate=1000000 ! h264parse ! flvmux streamable=true
  ! rtmpsink location="rtmp://... live=1"
  ```
- **验证**：日志出现 `===== NvVideo: NVENC =====`、`H264: Profile = 66` 即为硬编已启动。

### P2 Python 里 `rtmpsink location=URL live=1` 解析失败

- **现象**：`gst_parse_error: no property "live" in element "rtmpsink0" (2)`
- **根因**：`Gst.parse_launch()` 按空白切 token，`location=URL live=1` 被当成"给 rtmpsink 设一个叫 live 的属性"。而 120 的 shell 脚本 `rtmpsink location="$target_url live=1"` 能work，是因为整个串是**单个 argv**，gst-launch 只按第一个 `=` 切分，值里可以带空格 —— **shell 能过不代表 Python 能过**。
- **解法**：Python 里必须自己加**真·引号字符**把 `live=1` 并进 location 值：
  ```python
  tail = 'rtmpsink location="' + self.url + ' live=1"'   # 正确
  tail = 'rtmpsink location=\\"' + self.url + ' live=1\\"'  # 错：反斜杠转义不被当作引号
  ```
- **补充**：`gst-inspect-1.0 rtmpsink` 确认它**只有 `location` 属性**，没有 `live`，所以 `live=1` 只能塞进 location 串里。

### P3 RTMP 连不上服务器时"看起来在推"

- **现象**：`src.emit('push-buffer', buf)` 一直返回 OK，但播放器拉不到流。
- **根因**：appsrc 的 push 只到上游缓冲区，`rtmpsink` 的连接失败只体现在 **GStreamer 总线消息**里。
- **解法**：`RtmpPublisher` 挂 bus 监听，收集 ERROR/WARNING，暴露 `CheckError()`；主循环每 N 帧检查一次，报错就中止（日志里也能看到 `[gst ERROR]`）。
- **教训**：只凭 `push-buffer` 返回值判断推流健康是不够的。

### P4 `ros2 topic hz` 一条都收不到（两个原因叠加）

- **现象**：`ros2 topic list` 能看到 `/yolo/image_annotated`，但 `ros2 topic hz` 输出为空。
- **根因 1（QoS）**：发布端原本用 `qos_profile_sensor_data`（BEST_EFFORT），而 Foxy 的 `ros2 topic hz` **没有 `--qos-*` 参数**、固定用 RELIABLE 订阅。BEST_EFFORT 发布端 ↔ RELIABLE 订阅端 **不兼容**。
  - 解法：默认改为 `QoSProfile(depth=10)`（RELIABLE），并保留 `YOLO8_IMAGE_QOS=best_effort|sensor` 可切回。
  - 注意 rosbridge/Foxglove 不受影响：`rosbridge_library/internal/subscribers.py:112` 会读 endpoints 的 QoS 自动适配。
- **根因 2（缓冲）**：重定向到文件时 `ros2` 的输出是**块缓冲**，`timeout` 发 SIGTERM 杀进程 → 缓冲区丢失 → 文件空白。
  - 解法：`python3 -u /opt/ros/foxy/bin/ros2 topic hz <topic>`（`stdbuf -oL` 也行）。
- **验证**：修好后输出 `average rate: 8.008`。

### P5 Foxy 的 `logger.info()` 只接受单个字符串

- **现象**：`TypeError: info() takes 2 positional arguments but 7 were given`
- **根因**：Foxy（区别于 Humble+）RCUTILS 日志 API 不支持 `%s` 多参数格式化。
- **解法**：`self.get_logger().info('image publisher enabled on ' + str(topic))`。
- 顺带发现问题：103 上的 `lite3-ros-bridge.service` 就是这个原因每 3 秒崩一次（`ros_bridge_node.py:72`）。

### P6 命名空间包要按 `模块.类` 调用

- **现象**：`TypeError: 'module' object is not callable`（`pub = RtmpPublisher(sink=MODE)`）。
- **根因**：`from RtmpPublisher import RtmpPublisher` 在命名空间包下拿到的是**模块**不是类。
- **解法**：按原项目风格写 `RtmpPublisher.RtmpPublisher()`、`ROS2Transfer.ROS2Transfer()`。

### P7 `sys.path[0]` 是脚本所在目录

- **现象**：`src/test/` 下的脚本报 `ModuleNotFoundError: No module named 'ultralytics'`。
- **根因**：Python 把脚本所在目录（而非 cwd）放进 `sys.path[0]`。
- **解法**：测试脚本头部加
  ```python
  sys.path.insert(0, os.path.abspath(os.path.join(os.path.dirname(__file__), "..")))
  ```
- 原项目 `src/test/yolov8.py` 缺这一步，所以换个目录跑必挂。

### P8 headless 下 `cv2.waitKey` 抛异常

- **现象**：无桌面环境跑 tracking 主链路崩，报 OpenCV GUI 后端未实现（GTK）。
- **根因**：`RobotController.InputAndProcess()` **内部**会调 `cv2.waitKey(1)` 处理键盘输入，不是只有主入口在用。
- **解法**：`HEADLESS=1` 时在主入口 monkey-patch（只改本进程引用，不动业务代码）：
  ```python
  if headless:
      cv2.waitKey = lambda delay=1: -1
  ```
  同理 `cv2.destroyAllWindows()` 用 try/except 包住。

### P9 `RobotController.Run()` 在某些帧返回 None

- **现象**：偶尔整帧丢失、以为是程序退出。
- **根因**：`Run()` 里 `if(len(results)>0)` 才 return frame，否则隐式返回 None。
- **解法**：主循环必须 `skipped += 1; continue`，**不能**当成退出信号。

### P10 `cv2.UMat` 不能直接 JPEG 编码

- **解法**：`np_frame = frame.get() if hasattr(frame, 'get') else frame`。
  RobotController 的绘制路径会把 frame 转成 UMat，而 `cv2.imencode` 需要 ndarray。

### P11 长前台 SSH 命令被中断 + `/tmp` 日志丢失

- **现象**：一次 60s 的前台 ssh 命令返回空输出，`/tmp/*.log` 也不见了。
- **解法**：改用 `setsid nohup <cmd> > /home/test/yolo8/logs/xxx.log 2>&1 < /dev/null &` **脱离会话**，再分批轮询；日志目录用工程内的 `logs/`，不要依赖 `/tmp`。

### P12 启动期噪声不是故障

- `[TRT] [W] Using an engine plan file across different models of devices...` —— engine 跨设备加载的常规警告，实测推理正常。
- 启动阶段 ~32 条 `Stream format not found, dropping the frame` —— `nvv4l2decoder` 在 RTSP 首帧/首个关键帧到达前的正常输出，之后自动消失。
- **冷启动约 35s**（rtspsrc 建链 + TRT engine 加载），别用 20s 窗口判断"没起来"。

### P13 ReliabilityPolicy 枚举值不是 0/1

- `rclpy` 里 `RELIABLE=1`、`BEST_EFFORT=2`（不是直觉上的 0/1）。打印 QoS 标签时用 `int(reliability) == 2` 判断 best_effort，别想当然。

### P14 103 上没有 WS 客户端库

- `python3 -c "import websocket"` / `import websockets` 都失败 → 自己按 RFC6455 写了最小 WS 客户端 `src/test/verify_foxglove_path.py`（含握手、客户端帧掩码、分帧解析），零依赖验证 Foxglove 通路。

### B1 `set -o pipefail` 让"日志不存在"变成致命错误

- **现象**：`status all` 只输出第一个目标就中断，`echo $?` = 1。
- **根因**：`tail -n 3 日志 | sed` 中，日志文件不存在时 `tail` 返回 1，开了 `pipefail` 后整条流水线状态非 0，
  再遇 `set -e` 直接中止脚本。
- **解法**：日志相关操作统一走 `tail_log()` 兜底（`[ -f ] || return 0` + `|| true`）。

### B2 写在命令替换里的 `exit` 外层收不到

- **现象**：非法参数 `start badtarget` 打印了错误，但脚本仍以 0 退出且继续执行。
- **根因**：`for t in $(targets_of "$2")` —— `targets_of` 的 `exit 2` 只结束子 shell。
- **解法**：先取值再遍历 `list=$(targets_of "$2") || exit $?`。

### B3 `set -u` 与 ROS2 `setup.bash` 冲突

- **现象**：`source /opt/ros/foxy/setup.bash` 报
  `AMENT_TRACE_SETUP_FILES: unbound variable`，启动直接失败。
- **根因**：ROS2 自己的脚本会读未定义变量。
- **解法**：`set +u` → source → `set -u`。

### B4 `systemctl is-enabled` 对 disabled 返回非 0

- **现象**：`echo "enabled : $(systemctl is-enabled x || echo '?')"` 输出两行（第二行是 `?`）。
- **根因**：disabled 时 stdout 有值但退出码非 0，两个分支都执行，且命令替换是多行的。
- **解法**：先单独取值 `enabled=$(systemctl is-enabled "$unit" 2>/dev/null) || enabled=disabled`。

### B5 Windows 侧编辑脚本引入 CRLF

- **现象**：`/usr/bin/env: 'bash\r': No such file or directory`、`syntax error near unexpected token '{'`。
- **根因**：Windows 上用文本模式写 Python/batch 生成文件时 `\n` 被转成 `\r\n`。
- **解法**：写二进制（`newline=""` / `open(p,"wb")`），上传前扫一遍 `\r\n` 统一替换。

### B6 sudo 在非交互环境要 tty

- **现象**：自动 `exec sudo` 报 `a terminal is required to read the password`。
- **解法**：有 tty 才交互提权；无 tty 先试 `sudo -n`（需 NOPASSWD），失败就明确提示用户显式加 `sudo`。

### B7 "unit 已安装但未启用"被误判成 systemd 托管

- **现象**：只想手工起进程，`./start.sh` 却提示要 root、非交互下直接失败。
- **根因**：最初用 `unit 是否已安装` 作为"归 systemd 管"的判据，而默认状态下 unit 就是装着的（只是 disabled），
  于是手工启停也被迫走 systemctl。
- **解法**：判据改为 **installed **且** `systemctl is-enabled` 成功**：
  ```bash
  uses_systemd() { installed "$1" || return 1; systemctl is-enabled "$(unit_for "$1")" >/dev/null 2>&1; }
  ```
  未启用 → PID 文件直管进程（免 sudo）；已启用 → systemd 托管（自动提权）。

## 6. 2026-09-23 排查实录：「无红框」与「lite3 被踢」

用户反馈：① 走到相机前没有红框；② 开 YOLO 流后 `live/lite3` 被踢。
排查结论：**两个都是误判方向，真因各不相同**，以下为实证过程与修复。

### C1 「没有红框」＝看错了流

用户截图播放地址是 `http://172.31.68.227:8080/live/lite3.flv`——
这是 120 的**原始转发流**，从头到尾就没有标注框。
YOLO 标注流一直是另一路 `live/lite3_yolo`：

| 内容 | RTMP 地址 | HTTP-FLV 播放地址 |
| --- | --- | --- |
| 120 原始流（无框） | `rtmp://172.31.68.227:1936/live/lite3` | `http://172.31.68.227:8080/live/lite3.flv` |
| YOLO 标注流（红框） | `rtmp://172.31.68.227:1936/live/lite3_yolo` | `http://172.31.68.227:8080/live/lite3_yolo.flv` |

流名隔离的运行时证据：`yolo-publish.log` 里全部 14 次 URL 均为 `lite3_yolo`；
`RtmpPublisher` 默认值与 `deploy/yolo-publish.env` 也都是 `lite3_yolo`，从未推过 `lite3`。

### C2 「lite3 被踢」＝120 重启丢了 NAT，103 断网

- 实证：120 `uptime -s` = 2026-09-23 01:15:51（刚重启过），与用户测试时间窗重合。
- 链路：103 默认路由 `via 192.168.1.120`，出网必须 120 做 MASQUERADE。
  **120 开机脚本 `/home/ysc/host/host_start2.sh` 只给 192.168.2.0/24、192.168.137.0/24
  加了 NAT，漏了 103 的 192.168.1.0/24**（`master_start.sh` 里有但被注释；规则是易失的，
