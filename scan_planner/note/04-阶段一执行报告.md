### 关于日志中的 `a star error`（108 次）

这是 `dyn_a_star` 在**重规划瞬间**找不到路径时的重试报错（随机地图障碍密集，局部目标点偶尔落在障碍内）。
判定为**正常行为**，理由：
1. FSM 有 `fail_safe` + `max_replan_fail_count=1000` 的自恢复机制，报错后随即 `REPLAN_TRAJ → EXEC_TRAJ` 成功；
2. 最终状态是 `WAIT_TARGET`（到达），不是卡死；
3. 属于算法在随机地图上的表现，与 103 平台兼容性无关。

若想减少，可调 `fsm/planning_horizon`、`manager/*`，或降低 mockamap 的 `obstacle_number`（默认 500）。

## 六、阶段二修正：ros1_bridge 到底需不需要

**结论修正：输入侧完全不需要 bridge；只有"下发速度指令"这一个跨栈点需要，且只桥一条 Twist 消息。**

查证事实（103 实测）：

| 组件 | 路径 | ROS 版本 |
|---|---|---|
| 雷达驱动（MID360） | `/home/ysc/lite_cog/drivers/mid360_ws`（`devel/setup.bash` + `roslaunch livox_ros_driver2 msg_MID360s.launch`） | **ROS 1** |
| LIO | `/home/ysc/lite_cog/slam/src/faster-lio` | **ROS 1** |
| SCAN-Planner | `/home/test/scan_planner` | **ROS 1** |
| 机器人实时链路 | `transfer_ros2.service`（`lite_cog_ros2/transfer`，订阅 `/cmd_vel`） | **ROS 2 (foxy)** |

推论：

- **点云、里程计** → 与规划器同在 ROS 1 域，**原生直连，不要过桥**（`PointCloud2` 过桥要序列化/反序列化两次，Xavier NX 上代价很高）。
- **`/cmd_vel`** → 规划器在 ROS 1 域，机器人在 ROS 2 域，**这是唯一硬性的跨栈点**。

推荐做法（静态单话题桥接，开销最小）：

```bash
# 1) ROS1 侧：把规划器输出重命名为 /scan_planner/cmd_vel，避免与 ROS2 现有 /cmd_vel 撞车
#    （在 run.launch 里对 closed_loop_controller 做 remap）

# 2) 起静态桥（只桥一条 Twist，几十字节，CPU 可忽略）
source /opt/ros/noetic/setup.bash && source /opt/ros/foxy/setup.bash
ros2 run ros1_bridge parameter_bridge /scan_planner/cmd_vel@geometry_msgs/msg/Twist@geometry_msgs/Twist

# 3) 确认 ROS2 侧能收到后，再决定接入机器人指令口（人工确认环节，安全第一）
```

不建议 `dynamic_bridge`（会桥接所有话题，含大消息，CPU 与带宽代价大）。
