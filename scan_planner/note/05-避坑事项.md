## 1. 网络与软件源

### 1.1 ⚠️ 103 的联网状态随时间波动，必须实时复测

103 的上联是 **120 主机**（默认路由 `via 192.168.1.120`），因此"103 能不能出网"取决于 120 当时的状态。

- 实测记录：`01:24` DNS 全断 → 半小时后 `01:47` 自动恢复。
- **教训**：曾据此得出"103 没有外网"的结论，写入方案并据此设计了离线依赖方案，属于**错误结论**。
- **对策**：任何需要联网的步骤前先跑一次连通性测试，把结果**当场**记进日志，不要引用历史结论。

```bash
ping -c 2 223.5.5.5 && getent hosts github.com && echo "OK"
```

### 1.2 ⚠️ GitHub 直连不通（TCP 443 超时），走代理

直连 `20.205.243.166:443` 超时。可用通道按优先级：

| 通道 | 实测 | 备注 |
|---|---|---|
| 代理 `http://192.168.2.47:7897` | ✅ ping 1.8ms，`git clone --depth 1` 约 **4m29s**，成功拉到 122M 仓库 | 推荐，SOCKS5 也可用但更慢 |
| `https://gh-proxy.com/https://github.com/...` | `ls-remote` 通，完整 clone 比代理慢 | 兜底 |
| `gitclone.com` | ❌ 502 | 不要用 |

```bash
export http_proxy=http://192.168.2.47:7897
export https_proxy=http://192.168.2.47:7897
# apt 另需写 /etc/apt/apt.conf.d/01proxy
```

### 1.3 ⚠️ 清华 `ubuntu-ports` 镜像返回 403

`https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports/` 会让 `apt-get update` 退出码非 0（100）。
**注意**：这是源本身的问题，与代理无关，不要浪费时间排查代理链路。

**对策**：备份后整体替换为官方源（已固化到机器上）：

```bash
cp /etc/apt/sources.list /etc/apt/sources.list.bak.20260921
sed -i 's|https://mirrors.tuna.tsinghua.edu.cn/ubuntu-ports/|http://ports.ubuntu.com/ubuntu-ports/|g' /etc/apt/sources.list
```

可用的源：`packages.ros.org`（ROS1 + ROS2）、`repo.download.nvidia.com`、`ports.ubuntu.com`。

### 1.4 103 只有 IPv4

无全局 IPv6 地址、无 IPv6 默认路由。任何依赖 IPv6 的拉取方式都会失败。DNS 用 `223.5.5.5` / `119.29.29.29` 正常。

## 2. ROS1 / ROS2 共存环境

### 2.1 ⚠️ `~/.bashrc` 默认 source foxy

103 同时装了 `/opt/ros/noetic`（347 个包）和 `/opt/ros/foxy`。
`~/.bashrc` 第 139 行是 `source /opt/ros/foxy/setup.bash` —— **默认进入的是 ROS2 环境**。

不隔离直接跑 catkin 会出现难以定位的链接/ Python 路径错误。

### 2.2 必须做 ROS1 环境隔离（`scripts/env.sh`）

`scripts/env.sh` 做三件事，缺一不可：

1. `unset`：`AMENT_PREFIX_PATH`、`COLCON_PREFIX_PATH`、`ROS_VERSION`、`ROS_PYTHON_VERSION`、`ROS_DISTRO`
2. 从 `PYTHONPATH` 里**剔除** foxy 与 `lite_cog_ros2` 相关路径
3. 再 `source /opt/ros/noetic/setup.bash` → `source devel/setup.bash`
4. 设定 `ROS_MASTER_URI=http://127.0.0.1:11311`、`ROS_IP=192.168.1.103`

正确标志（每次进遥控器先确认）：

```
[env] ROS_DISTRO=noetic  AMENT=[]
```

### 2.3 常驻服务不要随手停

| 服务 | 说明 | 能否停 |
|---|---|---|
| `transfer_ros2.service` | 机器人实时链路 | ❌ 不要停 |
| `lite3-monitor.service` | 监控 | ⚠️ 可临时停以腾 CPU |

### 2.4 ⚠️ `roslaunch: command not found`

**现象**：新开终端直接敲 `roslaunch scan_planner lio_relay.launch` → `bash: roslaunch: command not found`。

**根因**：`~/.bashrc` 第 139 行 `source /opt/ros/foxy/setup.bash`，而 **foxy 里根本没有 `roslaunch`**
（ROS2 是 `ros2 launch`）。`roslaunch` 只存在于 ROS1：

```bash
ls -l /opt/ros/noetic/bin/roslaunch   # 存在
ls -l /opt/ros/foxy/bin/roslaunch     # No such file or directory
```

**对策**（二选一）：

```bash
# A. 先建环境，再敲命令
source /home/test/scan_planner/scripts/env.sh
roslaunch scan_planner lio_relay.launch

# B. 用封装脚本（内部自带 source，推荐）
bash /home/test/scan_planner/scripts/start_lio_relay.sh
bash /home/test/scan_planner/scripts/start_scan_real.sh
```

### 2.5 ⚠️ `ROS_MASTER_URI` 两边必须一致，否则各连各的 master

`.bashrc` 第 124 行是 `export ROS_MASTER_URI=http://192.168.1.103:11311`，
而 ROS1 的 `setup.bash` 一 source 就会把它重置成 `http://localhost:11311`。

**坑中坑**：如果在 source 之后才写 `export ROS_MASTER_URI=${ROS_MASTER_URI:-默认值}`，
读到的是被 setup.bash 改过的值，等于没设。必须在 source **之前**把原值存档。

`env.sh` 已处理（source 前存档 → source → 再写回）。正确标志：

```
[env] ROS_DISTRO=noetic  AMENT=[empty]
[env] ROS_MASTER_URI=http://192.168.1.103:11311  ROS_HOSTNAME=192.168.1.103
```

若两边 master 不同，表现为"找不到话题"或 `Unable to contact my own server`。

### 2.6 临时环境的备份与复原

`env.sh` 在改动**任何**环境变量之前，先把原值快照下来：

```bash
source scripts/env.sh          # 建环境，同时生成 logs/env_backup_<时间戳>_<pid>.sh
source scripts/env_restore.sh  # 关环境，精确复原（含"原本未设置"的变量）
```

覆盖的变量：`PATH`、`PYTHONPATH`、`LD_LIBRARY_PATH`、`PKG_CONFIG_PATH`、`CMAKE_PREFIX_PATH`、
`ROS_MASTER_URI`、`ROS_HOSTNAME`、`ROS_IP`、`ROS_DISTRO`、`ROS_VERSION`、`ROS_PYTHON_VERSION`、
`ROS_ROOT`、`ROS_ETC_DIR`、`ROS_PACKAGE_PATH`、`AMENT_PREFIX_PATH`、`COLCON_PREFIX_PATH`、
`ROS_DOMAIN_ID`、`RMW_IMPLEMENTATION`。

设计要点（都是踩过的）：

1. 原本没设的变量写 `unset`，不是写成空串，复原后才不会留下空壳变量；
2. 用 `printf %q` 转义，路径里有空格也不会坏；
3. **同一 shell 内重复 source 不会覆盖快照** —— 否则第二次会把 noetic 的值当成"原值"存下来，复原就失效了
   （靠 `SCAN_PLANNER_ENV_BACKUP` 标记判断）；
4. 未列入的变量（如 ROS2 的 `ROS_DOMAIN_ID` 之外那些）本来就没动，照原样。

实测往返：

```
建立后: ROS_DISTRO=noetic  ROS_DOMAIN_ID=7
恢复后: ROS_DISTRO=unset   ROS_DOMAIN_ID=7  RMW=rmw_cyclonedds_cpp
PATH: 已精确复原
```

查看历史快照：`ls -lt logs/env_backup_*.sh`；指定某一份复原：
`source scripts/env_restore.sh logs/env_backup_0923_023000_1234.sh`

## 3. 拉取与编译

### 3.1 ⚠️ 仓库根目录就是 workspace 根

SCAN-Planner 根目录**没有**顶层 `CMakeLists.txt`，`src/` 下直接就是各 ROS 包。
不要在外面再套一层 `src/`，否则 `catkin_make` 报找不到工作空间。

### 3.2 ⚠️ 分支选错：`ros2-community` 不能用

- `main` 分支：catkin + **ROS1 Noetic** ✅
- `ros2-community` 分支：Ubuntu 22.04 + Humble + C++17 ❌

103 是 Ubuntu 20.04 + Foxy，**不匹配**。实测采用 `main`，commit `348e8a5`。

### 3.3 ⚠️ 编译固定 `-j2`

6 核 / ~6.7 GiB 内存 + 3 GiB swap，PCL、OpenCV 头文件内存占用大。
实测 `-j2` 全量编译约 **14 分钟**，0 错误，内存未打满。**不要用 `-j6`**。

```bash
bash scripts/build.sh     # catkin_make -j2 -DCMAKE_BUILD_TYPE=Release，日志落 logs/
```

### 3.4 编译产物清单（用于确认是否编译完整）

`scan_planner/{scan_planner_node, closed_loop_controller, open_loop_controller, go2_kinematic_sim, go2_gait_publisher}`、

## 4. 桥接：这是最容易被过度设计的一环

### 4.1 ⚠️ 不需要全量桥接

曾一度认为需要把点云、里程计全部从 ROS1 桥到 ROS2。实际调查结果是：

| 数据源 | 所在栈 | 是否需要桥 |
|---|---|---|
| 雷达驱动 `/home/ysc/lite_cog/drivers/mid360_ws` | **ROS1** | ❌ 否 |
| FAST-LIO `/home/ysc/lite_cog/slam/src/faster-lio` | **ROS1** | ❌ 否 |
| SCAN-Planner | **ROS1** | — |
| 机器人执行链（`transfer_ros2.service` 消费 `/cmd_vel`） | **ROS2** | ✅ 是 |

**真正跨域的只有一个话题**：规划器输出的 `/cmd_vel`（`geometry_msgs/Twist`）。

### 4.2 正确做法：静态单话题桥

ROS1 侧先把输出 remap 到 `/scan_planner/cmd_vel`（避免与 ROS2 侧已有 `/cmd_vel` 撞名），然后：

```bash
ros2 run ros1_bridge parameter_bridge /scan_planner/cmd_vel@geometry_msgs/msg/Twist@geometry_msgs/Twist
```

**不要用 `dynamic_bridge`** —— 它会把两侧所有话题都拉起来，带来大量无用桥接与调试噪音。

### 4.3 ros1_bridge 可直接 apt 安装

不需要离线折腾依赖或源码编译：

```bash
apt install ros-foxy-ros1-bridge      # 实测候选 0.9.7-1focal arm64
```

## 5. 远程 Shell 操作（这两个坑各浪费过一次完整排查）

### 5.1 ⚠️ `pkill -f <pattern>` 会杀掉自己的 SSH 会话

**现象**：命令返回空 stdout、退出码 255 / SIGTERM，看不出任何错误信息。
**原因**：`ssh host '... pkill -f rosmaster ...'` 里，外层 shell 的命令行本身就包含 "rosmaster" 这个字符串，
`pkill -f` 匹配整个命令行 → 把自己的 shell 也杀了，**命令执行结果随之丢失**。

**对策**（二选一）：

```bash
pkill -9 -f 'rosmas[t]er'      # 方括号技巧：正则 rosmaster 不匹配字面 rosmas[t]er
```

或者把清理逻辑**写进脚本文件**再调用（脚本自身命令行不含模式串）。
`scripts/ab_test.sh` 用的就是后者。

⚠️ **`pgrep -f` 同样中招**：`for p in $(pgrep -f "scan_planner/devel/lib"); do kill -9 $p; done`
会把外层 shell 自己列进去并杀掉（表现为命令无输出、退出码 1）。同样用方括号：
`pgrep -f "scan_planner/devel/li[b]"`。

### 5.2 ⚠️ `cd dir && cmd &` 的后台化范围陷阱

```bash
cd /home/test/scan_planner && setsid nohup bash scripts/run_sim.sh > logs/x.log &   # 错
tail -5 logs/x.log      # → No such file or directory
```

`&` 作用于**整条 `A && B`**，于是 `cd` 发生在后台子 shell，前台仍停在原目录。
**对策**：把 `cd` 放进被调用脚本内部（`run_sim.sh` 已经这么做），或前台用 `( cd dir; cmd )` 显式子 shell。

### 5.3 Windows 侧校验 XML 的路径坑

沙箱 Python 对 `/tmp` 的解析与 Linux 不同，`python3 -c "... '/tmp/xxx.xml'"` 报 `FileNotFoundError`。
**对策**：用完整 Windows 路径：

```bash
python -c "import xml.dom.minidom as m; m.parse(r'C:/Users/19046/AppData/Local/Temp/xxx.xml'); print('XML OK')"
```

## 6. 仿真测试与日志判读 ⭐ 本章最贵的教训

### 6.1 ⚠️⚠️ 伪故障：测量本身会把被测系统测坏

**这是整个过程里代价最高的一次误判。**

第三轮手工测试（同样参数、同样地图）出现了严重劣化：

```
a star error            1139
drone is in obstacle     987
Replan failed 1000         1
日志行数               16374
```

据此一度判定"Lite3 参数是坏的"，准备回退。但改用**无人值守脚本**把完全相同的参数复跑两次：

```
V3a：a star error 0，drone is in obstacle 0，1000-fail 0，616 行  → 干净通过
V3b：a star error 20，drone is in obstacle 0，1000-fail 0，712 行 → 干净通过
```

**真相**：第三轮测试过程中，我在同一窗口里反复执行 `rostopic hz`、`rostopic echo`、`rosparam get` 进行探测。
Jetson 只有 6 核，`pcl_render_node` 的射线投射本来就吃满 CPU，被额外抢占后会拖慢感知闭环，
机器人偏离既定轨迹 → 撞进"刚发现"的障碍 → 触发 `drone is in obstacle` 连锁反应。

**对策（写进流程）**：
1. 度量窗口内**禁止**并行执行任何 `rostopic hz / echo / rosparam get`；
2. 回归判定一律交给无人值守脚本（`scripts/ab_test.sh`）；
3. 任何疑似劣化，**至少复跑两次**再下结论。

### 6.2 地图是确定性的，可以做真正可重复的 A/B

`mockamap` 在 `launch/simulator.xml` 里有固定配置，这让 A/B 对比成立：

| 项 | 值 |
|---|---|
| 随机种子 `seed` | **127**（固定） |
| 起点（navi_mode=1） | `(-19.0, 1.0, 0.25)` |
| 地图尺寸 | 40 × 40 × 5 m |
| 障碍 | type=2 随机盒子，`obstacle_number=500`，`height_min/max=2.0` |

所以**同一用例每次跑出来的地图完全一致**，参数才是唯一变量。

### 6.3 日志里的错误要分级，不要看到 ERROR 就判失败

| 日志 | 位置 | 含义 | 是否算失败 |
|---|---|---|---|
| `a star error` | `dyn_a_star` | 密集地图下 A\* 寻路重试 | ❌ 不算，算法有 `fail_safe` 自愈 |
| `ERROR! the drone is in obstacle. This should not happen.` | `bspline_optimizer.cpp:757` | 从被占点往前回溯，连第 0 个控制点都被占用 → **轨迹起点就在膨胀障碍里** | ✅ 严重信号 |
| `WARN! terminal point ... is in obstacle, skip this planning.` | 同上 `:773` | 终点不可达 | ⚠️ 关注 |
| `Suddenly discovered obstacles. emergency stop!` | FSM | 新发现障碍触发急停 | ⚠️ 关注频次 |
| `Replan failed 1000 times. Emergency stop and wait for a new target.` | FSM | 达到 `max_replan_fail_count` 上限 | ✅ 判定失败 |

**判定口径**：不要只看"有没有 ERROR"，要看 **终态 Pose + 是否出现 1000-fail / EMERGENCY_EXIT**。

### 6.4 ⚠️ `rosparam get` 报 "not set" 多半是名字写错

launch 里的 `<arg name="max_vel">` 到了运行时是**节点私有空间下的多个副本**，直接按 arg 名取会失败：

```bash
rosparam get /scan_planner_node/max_vel            # → ERROR: Parameter is not set
rosparam get /scan_planner_node/manager/max_vel          # → 0.75
rosparam get /scan_planner_node/optimization/max_vel     # → 0.75
```

不确定名字就先列：`rosparam list | grep max_vel`。

### 6.5 地图外 = 占用

`grid_map.h` 的 `getInflateOccupancyFromBuffer()` 在点位**不在地图边界内**时返回 `-1`，
而 `-1` 在 C++ 里是**真值**。所以"出地图边界"会被等价于"被占用"。
排查占用类问题时，别忘了先确认点位是否还在滑动地图范围内（10×10×5 m）。

## 7. Lite3 参数适配

### 7.1 双圆柱自碰撞包络：先搞清语义再改数

`plan_env/include/plan_env/grid_map.h:365`：

```cpp
inline int GridMap::getInflateOccupancy(Eigen::Vector3d pos, double yaw) {
  Eigen::Vector3d heading(std::cos(yaw), std::sin(yaw), 0.0);
  Eigen::Vector3d front = pos + mp_.double_cylinder_offset_ * heading;
  Eigen::Vector3d rear  = pos - mp_.double_cylinder_offset_ * heading;
  ...
}
```

即两个圆柱分别在机体**前后各偏移 `offset`** 处，各自半径 `radius`：

- 包络长度 = `2 × offset + 2 × radius`
- 包络宽度 = `2 × radius`

从 Lite3 官方 URDF（commit `549eb9ac`）实测推导：

| 来源 | 实测值 |
|---|---|
| TORSO 碰撞盒 | `0.5×0.1×0.12` 与 `0.25×0.2×0.12`（`origin z=0.01`） |
| 髋关节横向位置 | `0.1745`（前后）× `±0.062`，再加 HipY `0.09735` → 横向 ≈ **0.159** |
| 大腿 / 小腿 | `0.20` / `0.21012` → 站立髋高 ≈ **0.30** |

换算结果：

| 参数 | Go2 默认 | Lite3 现值 | 包络 |
|---|---|---|---|
| `double_cylinder_radius` | 0.25 | **0.18** | — |
| `double_cylinder_offset` | 0.18 | **0.12** | — |
| — | 0.86 m × 0.50 m | **0.60 m × 0.36 m** | 长 × 宽 |

### 7.2 ⚠️ `body_height` 在 navi_mode=1 下根本不生效

全代码只有两处引用，都在 navi_mode=3 的 `pathCallback` 里：

```
scan_replan_fsm.cpp:53   nh.param("grid_map/body_height", body_height_, 0.0);
scan_replan_fsm.cpp:374  msg->poses.back().pose.position.z + body_height_;
scan_replan_fsm.cpp:387  wp(2) = pose_stamped.pose.position.z + body_height_;
```

**2D Nav Goal（navi_mode=1）完全不读它。** 把 0.4 改成 0.30 是**正确的值**（符合 URDF 实测），
但**不要指望它对 navi_mode=1 的仿真回归产生任何影响**——它在那里是空操作。

### 7.3 ⚠️ `max_vyaw` 被源码硬钳位到 1.0

Lite3 SDK 允许 `vyaw` 到 1.5 rad/s，但 `closed_loop_controller.cpp` 里有：

```cpp
constexpr double kMaxVYawLimit = 1.0;
```

**改 launch 参数没用**，要跑满 1.5 必须改源码常量。首版保守按 1.0 用。

### 7.4 ⚠️ `max_vel := 1.0` 会触发急停连锁（已用无人值守脚本复核）

| 指标 | `max_vel=0.75`（V3a/V3b） | `max_vel=1.0`（V4） |
|---|---|---|
| 是否到达目标 | ✅ | ✅（仍到达） |
| `Replan failed 1000` | 0 | **1** |
| `EMERGENCY_STOP` | 0 | **3** |
| 日志行数 | 616 / 712 | **13979** |

**结论**：1.0 不是"跑不动"，而是**过于激进**——规划出的轨迹冲进尚未测绘区域，随后贴障反复重规划。
**仿真默认保持 0.75**；真机开阔场地才显式覆盖 `roslaunch ... max_vel:=1.0`。

### 7.5 Lite3 URDF 落地要点

新建包 `src/simulator/Utils/lite3_description/`：

- `package.xml` / `CMakeLists.txt` 由 `go2_description` 复制后 `sed` 改包名即可，**不要手写**
- 官方 URDF 的 mesh 路径是相对形式 `./meshes/xxx.STL`，必须改成 `package://lite3_description/meshes/xxx.STL`
- 4 个 STL（torso / hip / thigh / shank）共约 3.5 MB，走代理下载

`run.launch` 里加了可切换开关，方便对照：

```xml
<arg name="robot_pkg" default="lite3_description"/>
<!-- 切回 Go2: robot_pkg:=go2_description -->
```

### 7.6 ⚠️ 真机模式会叠加 Go2 的雷达外参，必须关掉

`advanced_param.xml` 原本把外参补偿直接绑死在真机开关上：

```xml
<param name="grid_map/need_extrinsic" value="$(arg is_real_world)" type="bool"/>   <!-- 旧 -->
```

而 `grid_map.cpp:57` 里硬编码的是 **Go2 的雷达→机体平移**：

```cpp
mp_.lidar_extrinsic_ <<
    1.0, 0.0, 0.0, -0.01100,
    0.0, 1.0, 0.0, -0.02329,
    0.0, 0.0, 1.0,  0.04412,
    0.0, 0.0, 0.0,  1.00000;
```

103 的 FAST-LIO 给出的**已经是机体系**（`/Odometry` 的 `child_frame_id="body"`、
`/cloud_registered_body` 的 `frame_id="body"`），再叠这个 Go2 外参就是错的
（约 5 cm 系统误差，对站立高度 0.30 m 的 Lite3 影响明显）。

**已修**：抽出独立 arg，默认值保持原逻辑不变（仿真不受影响），真机显式关闭：

```xml
<arg name="need_extrinsic" default="$(arg is_real_world)"/>
<param name="grid_map/need_extrinsic" value="$(arg need_extrinsic)" type="bool"/>
```

```bash
roslaunch scan_planner run.launch is_real_world:=true need_extrinsic:=false ...
```

### 7.7 真机安全网：绝不直接发裸 `/cmd_vel`

`closed_loop_controller.cpp:239` 发布的是相对名 `cmd_vel` → 解析为 `/cmd_vel`，
而 ROS2 侧的 `transfer_ros2.service` 正在消费 `/cmd_vel`。一旦桥接存在就会直接驱动机器人。

**已修**（`run.launch`）：真机模式强制改道：

```xml
<node pkg="scan_planner" name="closed_loop_controller" type="closed_loop_controller" output="screen">
  <remap if="$(arg is_real_world)" from="cmd_vel" to="/scan_planner/cmd_vel"/>
</node>
```

实测验证：真机模式下 `/scan_planner/cmd_vel` 存在、裸 `/cmd_vel` 数量为 **0**。

### 7.8 ⚠️ XML 注释里不能出现连续两个短横

写 launch 注释时用 `-------` 做分隔线会直接让 `roslaunch` 解析失败
（`not well-formed (invalid token)`）。XML 规范禁止注释内出现 `--`。
**用 `====` 做分隔线。** 本机改 `lio_relay.launch` 时踩过一次。

### 7.9 ⚠️ 步态发布器只能仿真用

`go2_kinematic_sim` 依赖 `go2_gait_publisher` 发布的 `quad_0` 步态 Topic。
真机上不能启动它，已加保护：

```xml
<node unless="$(arg is_real_world)" pkg="scan_planner" name="go2_gait_publisher" .../>
```

## 10. FAST-LIO 话题适配（本机已实测）

### 10.1 问题现象

`mapping_c16.launch` **不做任何 remap**，节点用的是源码里的默认话题名，
而 SCAN-Planner 真机模式只认 `/LIO/*`。两者对不上：

| SCAN-Planner 期望 | FAST-LIO 实际发布 | 类型 / frame |
|---|---|---|
| `/LIO/odom_vehicle` | `/Odometry` | `nav_msgs/Odometry`，`frame_id=camera_init`，`child_frame_id=body` |
| `/LIO/odom_imu` | ——（无独立 IMU 话题） | 复用 `/Odometry` |
| `/LIO/clouds_lidar` | `/cloud_registered_body` | `PointCloud2`，`frame_id="body"`，**未降采样，更密** |

源码出处（`src/laser_mapping.cc`）：

```
262  pub_laser_cloud_world_  -> /cloud_registered           (frame camera_init, dense_publish_en=false 时是降采样)
263  pub_laser_cloud_body_   -> /cloud_registered_body      (frame body, 来自 scan_undistort_, 完整点数)
265  pub_odom_aft_mapped_    -> /Odometry
266  pub_path_               -> /path                        (c16.yaml 里 path_publish_en=false)
```

选 `/cloud_registered_body` 而不是 `/cloud_registered` 的理由：
`PublishFrameBody()` 发的是 `scan_undistort_` 全量点，而世界系那份在 `dense_publish_en=false`
时走的是 `scan_down_world_`（降采样），局部建图用前者更密。

### 10.2 解决方案：`lio_relay.launch`

新增 `src/planner/plan_manage/launch/lio_relay.launch`，用 `topic_tools relay` 纯转发：

```xml
<node pkg="topic_tools" type="relay" name="lio_odom_vehicle_relay" args="/Odometry /LIO/odom_vehicle"/>
<node pkg="topic_tools" type="relay" name="lio_odom_imu_relay"     args="/Odometry /LIO/odom_imu"/>
<node pkg="topic_tools" type="relay" name="lio_cloud_relay"        args="/cloud_registered_body /LIO/clouds_lidar"/>
```

好处：**不改动 ysc 的 slam 仓库**，`gridmap.sh` / `save_map.sh` / rviz 照常工作；
relay 直接转发收到的消息对象（不深拷贝），开销可忽略；SLAM 先起来之后再启它也行。

备选：想用世界系点云就 `roslaunch scan_planner lio_relay.launch cloud_in:=/cloud_registered`，
同时 SCAN-Planner 侧要 `cloud_is_world:=true`（`grid_map.cpp` 里 `cloud_is_world=true` 分支
直接把点当世界坐标用，不做旋转平移）。

### 10.3 真机模式下的坐标系约定（重要）

`grid_map.cpp` 里 `sensorPoseCallback` 拿 `sensor_pose` 当射线原点；若 `need_extrinsic=true`
会再叠 `mp_.lidar_extrinsic_`（Go2 的 −0.011/−0.02329/+0.04412）。
我们喂的是**机体系位姿 + 机体系点云**，所以：

- `cloud_is_world=false`（真机默认值，正确）
- **`need_extrinsic` 必须 false**（见 7.6）
- `body_pose` 只用于滑动地图窗口跟随（`slidingMapFrameCallback` 只取 x/y/z），与 `sensor_pose` 同源无妨
